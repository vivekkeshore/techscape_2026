Part 1

01

Deterministic workflows: code controls the execution

[11:00] Part 1 - the two patterns where your code owns the control flow: Planning and Voting.

Pattern 01 · Planning

Ask for a plan once, then execute it in a loop

[11:00 – 12:30] Planning: ask the model for a plan, then execute it in a loop. make_plan: one call returns three ordered steps as JSON. That one call decides the shape of all the work. build: each step is a separate call with a small brief - what's already done, and exactly this one step. [Advance] The code animates into the next slide - the plan call and the loop.

Pattern 01 · Planning

The model writes the plan. The code runs it.

[12:30 – 13:00] One call shapes all the work: make_plan. [Advance] The for loop: the model has no say in the order. The code owns it. [Advance] The callout: the model writes the plan, the code runs it. If asked "isn't the plan different every run?": yes - the plan's content varies, but its execution doesn't. The model can't skip, add, reorder or loop back. Need the same plan every time? Freeze it: review it, save it as a spec, and replay it. Output: PLAN: design the data model, write the endpoints, add tests - then 1/3, 2/3, 3/3.

Pattern 01 · Planning

Every failure stays local

Why it works

  • The plan can be a spec
  • Small brief per step keeps context small
  • Step 3 produces garbage? Rerun step 3 only

Gates after each step

  • Does the artifact exist?
  • Do the tests pass?
  • Does the app compile and run?

A failed gate retries one step, not the whole run.

Use it when

You already know the scope of work

Periodic reports, same sections Scaffold: DB model before API

It hurts when

The next step depends on what the last one found.

A fixed plan can't react - it confidently runs a stale plan.

[13:00 – 15:00] The plan comes first - it can even be a spec document. Each step gets a small brief, which keeps context small. Failures are localised: if step three produces garbage, you rerun step three only. Real implementations add a dependency graph and a checkpoint after each step: does the artifact exist, do tests pass, does it compile and run. A failed checkpoint retries one step instead of restarting everything. Use it when you know the scope - a weekly report always has the same sections, a scaffold always needs a data model before an API. It hurts when step N+1 genuinely depends on what step N discovered. A fixed plan can't react, so it confidently executes a stale plan.

Pattern 02 · Voting / Consensus

Ask several times independently - let the code decide

[15:00 – 16:00] Voting: ask several times independently, then let code decide what the answers mean. One contract clause, five reviewers, each with a single lens: liability, privacy, finance, commercial, regulatory. They run in parallel in a thread pool - independent calls. Multiprocessing works too. [Advance] The code animates into the next slide - the last three lines are the ones that matter.

Pattern 02 · Voting / Consensus

The policy is code, not a prompt.

[16:00 – 16:30] The decision policy - three or more agreeing, otherwise escalate - is code, not a prompt. [Advance] The callout appears: "The policy is code, not a prompt." Pause on it - you can test it, version it and audit it; a prompt you can only hope about.

Pattern 02 · Voting / Consensus

Disagreement is a result, not a problem

Five lenses, one clause

liability BLOCK privacy ACCEPT finance NEGOTIATE commercial NEGOTIATE regulatory ACCEPT

tally 1 : 2 : 2  →  ESCALATE

1. Reviewers never see each other's answers.

Otherwise: five copies of one opinion.

2. Never break the tie.

1 : 2 : 2 is the answer - escalate it.

Policies live in code: a liability BLOCK can veto any count.

[16:30 – 18:30] The output: one BLOCK, two ACCEPT, two NEGOTIATE. No option reaches three, so the code escalates. Two points make or break this pattern, and both are easy to get wrong. One: reviewers must not see each other's responses. If they do, their errors correlate and you get five copies of one opinion. Two: disagreement is the result. A distribution like 2:2:1 is a measurement. Hand it to a human, another agent or plain Python. If you try to break the tie, you destroy the only information the pattern produced. Policies such as "a liability BLOCK vetoes everything" belong in code.

Pattern 02 · Voting / Consensus

Buy confidence only when being wrong is expensive

Use it when

A wrong answer is costly, and code or judgement can check it

Compliance review Medical triage

It hurts when

Cost matters more than confidence

Chat replies Autocomplete
5×

the price of a single call - every run

[18:30 – 19:30] [Advance] Use voting when a wrong answer is expensive - compliance review, medical triage. [Advance] Don't use it when cost matters more than confidence - high-volume, low-stakes calls like chat replies or autocomplete. [Advance] This example costs five times a single call on every run. That wraps up the deterministic family.

Part 2

02

Autonomous agents: the LLM controls the execution

[19:30] Part 2 - four patterns where the model owns at least part of the control flow: ReAct, Reflection, Collaboration, Supervisor.

Pattern 03 · ReAct

Think→ Pick a tool→ Read the output→ Think again ↺
[19:30 – 21:00] ReAct = Reason + Act. It's a loop: the model thinks, picks a tool, reads the output, thinks again. Two tools: check_stock and reorder. The system prompt defines a tiny protocol: emit either "Action: tool(args)" or "Done: answer". [Advance] The code animates into the next slide - the loop.

Pattern 03 · ReAct

The model picks each action. The code caps the steps.

[21:00 – 21:30] The loop: ask, stop on Done, otherwise parse the action, run the tool, and append the observation to the transcript. Note the range(6) - the step cap lives in code, not in the prompt. [Advance after the last code step] The callout: the model picks each action, the code caps the steps.

Pattern 03 · ReAct

The path is discovered, not declared

Action: check_stock(SKU-4417) Observation: SKU-4417: 6 units on hand Action: reorder(SKU-4417, 120) Observation: created a PO for 120 units of SKU-4417 Done: Only 6 units were left before a promo, so I ordered 120 more.

No line of code says "check stock first". The model chose it.

The step cap

Without it, a confused agent loops until you see the bill.

Use it when

You can't know the path in advance

Debugging Incident response Live ticker prices

It hurts when

The path is knowable - you pay to rediscover it on every run

[21:30 – 23:30] Look at what happened. The loop decides almost nothing: parse, run, append, repeat. The model checked stock, saw 6 units, then reordered 120. No line of code said "check stock before reordering." The reorder was an action based on the reasoning over the first observation. That's the whole value proposition: the path is discovered, not declared. The step cap matters: a confused or hallucinating agent will loop until you notice your bill. Use it when the path is unknowable up front - debugging, incident response, live data investigation. It hurts when the path is known or knowable: you pay per model call to rediscover a sequence you could write down once. That's Planning's job.

Pattern 04 · Reflection

One call does the work, another call attacks it

The briefMeta description for a rechargeable trail headlamp · max 155 characters
[23:30 – 24:30] Reflection: the first call produces the work, a second call with a different job attacks it. lint() is plain Python - never pay a model to count characters. Each round: write a draft that addresses the known issues, then a hostile reviewer judges it. [Advance] The code animates into the next slide - how a round ends.

Pattern 04 · Reflection

Two judges: lint for the rules, the critic for the quality.

[24:30 – 25:00] Issues = lint failures + critic failures. No issues? Stop. The loop runs until the critic is satisfied or the ceiling of 3 rounds is hit. Because the length isn't fixed, this is an autonomous pattern, not a two-step workflow. [Advance] The callout: two judges - lint for the rules, the critic for the quality.

[Advance] Round 2: 126 characters, specific numbers, approved. Give the critic a different job: find what's wrong. Don't make it redo the writer's work.

Pattern 04 · Reflection

Rules go in code, judgement goes to the model

Rule of thumb

If code can check it, don't ask the model.

character countsbanned phrases required keywordsschema validation

Use it when

  • First drafts aren't good enough
  • Failure modes are hard to specify up front
Code review Vulnerability patching

It hurts when

The judgement is deterministic

If a test suite can decide, run the tests.

[26:00 – 27:00] [Advance] Rule of thumb: if code can check it, don't ask the model - character counts, banned words, required keywords, schema validation. Use the model only for judgement: is the CTA specific, is the claim quantified. [Advance] Use it when first drafts are insufficient or failure modes are hard to specify - code review, vulnerability patching. [Advance] It hurts when the judgement is deterministic. If tests can say whether the work is correct, run the tests.

Pattern 05 · Collaboration

Specialists hand work to each other - no manager

[27:00 – 28:00] Collaboration: specialist agents hand the work to each other. No manager, no supervisor. Three peers: copywriter, art director, compliance. Every peer sees the whole thread, does its part, and picks who goes next - as JSON. range(8) is the cycle guard, in code. [Advance] The code animates into the next slide - the handoff.

Pattern 05 · Collaboration

The model picks who goes next - even backwards.

[28:00 – 28:30] Each peer's work lands in the shared thread; "done" ends the run. [Advance] The last line: a peer can hand work backwards. [Advance] The callout: the model picks who goes next - even backwards.

[28:30 – 30:30] Six handoffs happened, but handoff 3 is where the pattern proves itself. Look at handoffs 1–3 in isolation: copywriter, art director, compliance. That's indistinguishable from a hard-coded pipeline. If compliance had approved, you'd have no evidence you were looking at anything but three sequential stages. That backward handoff makes this a mesh and not a pipeline, and no supervisor was needed.

[30:30 – 31:30] [Advance] The cost of that freedom is cycles. Compliance and copywriter could hand off to each other indefinitely. Pattern 06 · Supervisor

One manager - workers see only their assignment

The ticketCharged twice since the SSO cutover · unfamiliar login IPs · renewal in 3 weeks
[31:30 – 32:30] Supervisor: one manager, workers that only see their assignment. The ticket: an enterprise customer was charged twice since the SSO cutover, and security sees logins from unknown IP ranges. Renewal in three weeks. Step 1: the boss assigns tasks to billing and platform workers. Step 2: each worker gets the ticket plus its own task. Step 3: the boss combines the reports into one customer answer. Pattern 06 · Supervisor

A worker sees its task - nothing else.

[32:30 – 33:00] Back to the workers. [Advance] Line 9: the ticket plus its own task - that's a worker's entire context. [Advance] The callout: a worker sees its task, nothing else.

Pattern 06 · Supervisor

One f-string is the isolation boundary f"Ticket: {TICKET}\n\nYour task: {job['task']}"
billing Two charges four days apart. A duplicate org entity was billed twice. platform SCIM still pointed at the old directory and created a second org. RESOLUTION: One misconfigured cutover created a duplicate org record. That single fault caused both the double invoice and the unfamiliar logins, which came from our own provisioning range.
  • Ticket plus own task - no sibling reports, no manager reasoning, no history
  • Small contexts; workers run in parallel
  • One worker's wrong guess can't become another worker's premise
[33:00 – 33:45] Say it plainly: one f-string is the isolation boundary. The line doing the heavy lifting is the single f-string that builds the worker prompt: the ticket plus the worker's own task, and nothing else. [Advance] No sibling reports, no manager reasoning, no history. [Advance] So every context stays small, and workers can run in parallel. [Advance] And one worker's wrong guess can't become another worker's premise. The result: the supervisor connected two separate symptoms to one root cause.

Before you reach for any pattern

Four checks - one "no" means change the design

01

Is the task genuinely multi-step and hard to fully specify?

02

Does the outcome justify the cost and latency?

03

Do you actually need the model to do it?

04

Can you catch errors, and can the app recover from them?

Source: Anthropic, Building effective agents

[37:00 – 38:00] Four checks from Anthropic's own guidance on when to build an agent and when not to. Is the task genuinely multi-step and hard to specify? Does the outcome justify cost and latency? Is the model actually needed? Can errors be caught and recovered from? A single "no" means change your design. This one paragraph alone explains where most teams go wrong.
