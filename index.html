Two families

Where does the execution path live?

Deterministic workflows

The path lives in your source code

  • Calls a model one or more times
  • You read the flow straight from the code
  • The same input takes the same route

Autonomous agents

The LLM decides the path

  • The model picks tools, judges progress and chooses who goes next
  • Solves problems whose steps you can't know in advance
  • The same input may take a different route
  • Reproducibility becomes a challenge
[6:30 – 8:00] Walk through both columns. Deterministic: the model is a function you call; the "if/for/while" belongs to you. Rerun it and you get the same route. Autonomous: the model decides which tool to call, whether the work is done, and who handles it next. That's what lets it solve open-ended problems — and it's also why reproducibility gets hard.

The most expensive mistake

Neither family is more advanced. But picking autonomous where deterministic fits costs you twice — in tokens, and in non-determinism you never needed.
[8:00 – 9:00] This is the central warning. Autonomous is not "level 2" of deterministic. They are different tools. Choosing autonomy you didn't need is the most expensive mistake: you pay in tokenomics, and you pay with non-determinism — harder debugging, flaky tests, surprising bills.

Part 1

01

Deterministic workflows: code controls the execution

[11:00] Part 1 — the two patterns where your code owns the control flow: Planning and Voting.

Pattern 01 · Planning

Ask for a plan once, then execute it in a loop

[11:00 – 13:00] Planning: ask the model for a plan, then execute it in a loop. make_plan: one call returns three ordered steps as JSON. That one call decides the shape of all the work. build: each step is a separate call with a small brief — what's already done, and exactly this one step. The for loop: the model has no say in the order. The code owns it. Output: PLAN: design the data model, write the endpoints, add tests — then 1/3, 2/3, 3/3.

Pattern 01 · Planning

Every failure stays local

Why it works

  • The plan can be a spec
  • Small brief per step keeps context small
  • Step 3 produces garbage? Rerun step 3 only

Gates after each step

  • Does the artifact exist?
  • Do the tests pass?
  • Does the app compile and run?

A failed gate retries one step, not the whole run.

Use it when

You already know the scope of work

Periodic reports, same sections Scaffold: DB model before API

It hurts when

The next step depends on what the last one found. A fixed plan can't react — it confidently runs a stale plan.

[13:00 – 15:00] The plan comes first — it can even be a spec document. Each step gets a small brief, which keeps context small. Failures are localised: if step three produces garbage, you rerun step three only. Real implementations add a dependency graph and a checkpoint after each step: does the artifact exist, do tests pass, does it compile and run. A failed checkpoint retries one step instead of restarting everything. Use it when you know the scope — a weekly report always has the same sections, a scaffold always needs a data model before an API. It hurts when step N+1 genuinely depends on what step N discovered. A fixed plan can't react, so it confidently executes a stale plan.

Pattern 02 · Voting / Consensus

Ask several times independently — let the code decide

[15:00 – 16:30] Voting: ask several times independently, then let code decide what the answers mean. One contract clause, five reviewers, each with a single lens: liability, privacy, finance, commercial, regulatory. They run in parallel in a thread pool — independent calls. Multiprocessing works too. The last line is the important one: the decision policy — three or more agreeing, otherwise escalate — is code, not a prompt.

Pattern 02 · Voting / Consensus

Disagreement is a result, not a problem

Five lenses, one clause

liability BLOCK privacy ACCEPT finance NEGOTIATE commercial NEGOTIATE regulatory ACCEPT

tally 1 : 2 : 2  →  ESCALATE

1. Reviewers must never see each other's answers.

The moment they can, their errors correlate and they converge on one opinion.

2. Never break the tie.

One call gives you confidence. Five calls give you a distribution — 3:2, 2:2:1. Escalating to a human or another agent is the feature; forcing a tie-break throws away the only information the pattern produces.

Policies live in code: a BLOCK from the liability reviewer can veto regardless of the count.

[16:30 – 18:30] The output: one BLOCK, two ACCEPT, two NEGOTIATE. No option reaches three, so the code escalates. Two points make or break this pattern, and both are easy to get wrong. One: reviewers must not see each other's responses. If they do, their errors correlate and you get five copies of one opinion. Two: disagreement is the result. A distribution like 2:2:1 is a measurement. Hand it to a human, another agent or plain Python. If you try to break the tie, you destroy the only information the pattern produced. Policies such as "a liability BLOCK vetoes everything" belong in code.

Pattern 02 · Voting / Consensus

Buy confidence only when being wrong is expensive

Use it when

Being wrong is expensive, and judgement or rules in code can check correctness

Compliance review Medical triage

It hurts when

Cost matters more than confidence

5×

the price of a single call — every time

[18:30 – 19:30] Use voting when a wrong answer is expensive — compliance review, medical triage. Don't use it when cost matters more than confidence: this example costs five times a single call on every run. That wraps up the deterministic family.

Part 2

02

Autonomous agents: the LLM controls the execution

[19:30] Part 2 — four patterns where the model owns at least part of the control flow: ReAct, Reflection, Collaboration, Supervisor.

Pattern 03 · ReAct

Think→ Pick a tool→ Read the output→ Think again ↺
[19:30 – 21:30] ReAct = Reason + Act. It's a loop: the model thinks, picks a tool, reads the output, thinks again. Two tools: check_stock and reorder. The system prompt defines a tiny protocol: emit either "Action: tool(args)" or "Done: answer". The loop: ask, stop on Done, otherwise parse the action, run the tool, and append the observation to the transcript. Note the range(6) — the step cap lives in code, not in the prompt.

Pattern 03 · ReAct

The path is discovered, not declared

Action: check_stock(SKU-4417) Observation: SKU-4417: 6 units on hand Action: reorder(SKU-4417, 120) Observation: created a PO for 120 units of SKU-4417 Done: Only 6 units were left before a promo, so I ordered 120 more.

The loop decides almost nothing: parse, run, append, repeat. Nothing in the code says "check stock before reordering."

The step cap

A confused or hallucinating agent loops until you notice your bill.

Use it when

You can't know the path in advance

Debugging, incident response Live data, e.g. ticker prices

It hurts when

The path is known or knowable — you pay per call to rediscover a sequence you could write down once

[21:30 – 23:30] Look at what happened. The model checked stock, saw 6 units, then reordered 120. No line of code said "check stock before reordering." The reorder was an action based on the reasoning over the first observation. That's the whole value proposition: the path is discovered, not declared. The step cap matters: a confused or hallucinating agent will loop until you notice your bill. Use it when the path is unknowable up front — debugging, incident response, live data investigation. It hurts when the path is known or knowable: you pay per model call to rediscover a sequence you could write down once. That's Planning's job.

Live demo · ReAct against a real repository

Real tools, a real bug, a real fix

The bug · shop/cart.py

A flat ₹100 coupon gets subtracted after 18% GST: ₹1080 instead of ₹1062. Two of three tests pass — that's why it shipped.

Five real tools

run_tests()list_files()read_file()grep()apply_fix()

Watch for

  • It starts from the real failure, not a guess about it
  • It checks pricing.py before editing — the fix lands in the caller
  • It re-runs the tests: "a fix I have not seen pass is not a fix"
  • Then code re-runs them again, after the loop — not the agent's word for it

Run it

[≈3:00, live] Switch to the terminal. Font size up (Cmd +) before the talk. Setup: a tiny checkout package is written to a temp dir. It genuinely has a bug. The tools really run unittest, read files, and edit disk. Without an API key, only the model's decisions are replayed from a recording — every observation is real. Pattern 04 · Reflection

One call does the work, another call attacks it

Brief: meta description for a rechargeable trail headlamp, max 155 characters.

[23:30 – 25:00] Reflection: the first call produces the work, a second call with a different job attacks it. lint() is plain Python — never pay a model to count characters. Each round: write a draft that addresses the known issues, then a hostile reviewer judges it. Issues = lint failures + critic failures. No issues? Stop. The loop runs until the critic is satisfied or the ceiling of 3 rounds is hit. Because the length isn't fixed, this is an autonomous pattern, not a two-step workflow.

Pattern 04 · Reflection

Code checks the rules, the model judges the quality

Round 1 · 190 characters

"Discover the best-in-class TrailLight 2, a revolutionary rechargeable trail headlamp built for serious night runners, with a huge 40-hour burn time and an ultra-bright beam. Buy yours today."

lint: 190 characters, limit is 155
critic: 'best-in-class' is filler and the CTA is generic

Round 2 · 126 characters

"TrailLight 2: a rechargeable trail headlamp with 40-hour burn time and a 400-lumen beam for night runs. See sizes and pricing."

APPROVED

Regex can do it? Code does it

Character counts, banned phrases, required keywords, schema validation.

Use it when

First drafts aren't good enough and failure modes are hard to specify up front

Code reviewVulnerability patching

It hurts when

The judgement is deterministic. If a test suite can decide, run the tests — don't ask for an opinion.

[25:00 – 27:00] Round 1 failed twice: lint caught 190 characters against a limit of 155 with full reliability, and the critic caught "best-in-class" filler and a generic CTA. Round 2: 126 characters, specific numbers, approved. Rule of thumb: anything a regex can do goes in code — character counts, banned words, required keywords, schema validation. Use the model only for judgement: is the CTA specific, is the claim quantified. Give the critic a different job: find what's wrong. Don't make it redo the writer's work. Use it when first drafts are insufficient or failure modes are hard to specify — code review, vulnerability patching. It hurts when the judgement is deterministic. If tests can say whether the work is correct, run the tests.

Pattern 05 · Collaboration

Specialists hand work to each other — no manager

[27:00 – 28:30] Collaboration: specialist agents hand the work to each other. No manager, no supervisor. Three peers: copywriter, art director, compliance. Every peer sees the whole thread, does its part, and picks who goes next — as JSON. range(8) is the cycle guard, in code. And the last line: a peer can hand work backwards.

Pattern 05 · Collaboration

Handoff 3 proves the pattern

1copywriterHeadline: One cup. Every refill.→ art_director
2art_directorOverhead shot of one cup, faint coffee rings, morning light.→ compliance
3complianceREJECTED: "plastic-free" is unsupported — the lid gasket is silicone.↩ copywriter
4copywriterHeadline: Your 4th coffee of the day, same cup.→ art_director
5art_director2×2 grid: the same cup at four times of one workday.→ compliance
6complianceAPPROVED. Every claim is substantiated.✓ done

One rejection propagated through two peers. A new headline invalidated the image direction too — and nothing scheduled that rework. A peer chose it mid-run.

[28:30 – 30:30] Six handoffs happened, but handoff 3 is where the pattern proves itself. Look at handoffs 1–3 in isolation: copywriter, art director, compliance. That's indistinguishable from a hard-coded pipeline. If compliance had approved, you'd have no evidence you were looking at anything but three sequential stages. [Advance] At handoff 3, compliance read the thread and sent the work back to the copywriter, who had already had a turn. [Advance] The new headline also invalidated the image direction, so the art director ran again. One rejection propagated through two peers. That backward handoff makes this a mesh and not a pipeline. Nothing scheduled the rework loop, and no supervisor was needed.

Pattern 05 · Collaboration

Freedom costs cycles

Compliance and the copywriter can bounce work between them forever. The guardrail doesn't have to be clever: a ceiling in code, or a cap on visits per peer.

Use it when

The work is a chain of specialists, and each handoff needs the previous specialist's output

Creative pipelineMulti-stage routing

It hurts when

You need one accountable answer — nobody in a mesh of specialists owns the outcome

[30:30 – 31:30] The cost of that freedom is cycles. Compliance and copywriter could hand off to each other indefinitely. The guardrail can be as simple as a ceiling number in code, or a per-peer visit cap. Use it for chains of specialists where each needs the previous output — creative pipelines, multi-stage routing. It hurts when you need a single accountable answer, because nobody in the mesh owns the outcome. Which brings us to the Supervisor.

Pattern 06 · Supervisor

One manager — workers see only their assignment

Ticket: charged twice in March since the SSO cutover, and unfamiliar login IP ranges — renewal in three weeks.

[31:30 – 33:00] Supervisor: one manager, workers that only see their assignment. The ticket: an enterprise customer was charged twice since the SSO cutover, and security sees logins from unknown IP ranges. Renewal in three weeks. Step 1: the boss assigns tasks to billing and platform workers. Step 2: each worker gets the ticket plus its own task — that's its entire context. Step 3: the boss combines the reports into one customer answer.

Pattern 06 · Supervisor

One f-string is the isolation boundary

billing Two charges four days apart. A duplicate org entity was billed twice. platform SCIM still pointed at the old directory and created a second org. RESOLUTION: One misconfigured cutover created a duplicate org record. That single fault caused both the double invoice and the unfamiliar logins, which came from our own provisioning range.
  • Ticket plus own task — no sibling reports, no manager reasoning, no history
  • Small contexts; workers run in parallel
  • One worker's wrong guess can't become another worker's premise

Use it when

The request splits into independent specialist questions, and someone must own the combined answer

Codebase understandingMulti-analyst research "Search these six subsystems"

It hurts when

Workers depend on each other. The supervisor carries every cross-cutting decision — if workers need each other's raw output, use Collaboration.

[33:00 – 34:30] The line doing the heavy lifting is the single f-string that builds the worker prompt. It's the isolation boundary: the ticket plus the worker's own task, and nothing else. No sibling reports, no manager reasoning, no history. So every context stays small, workers can run in parallel, and one worker's wrong guess can't become another worker's premise. The result: the supervisor connected two separate symptoms to one root cause. The price: every cross-cutting decision happens in the supervisor. If two workers genuinely need each other's raw output, Collaboration fits better. Use it when the request splits into independent specialist questions and someone must own the combined answer — codebase understanding, multi-analyst research.

Read them in pairs

The patterns teach more against each other than alone

Planning vs ReAct

Same job shape, opposite control flow

Planning fixes the order. ReAct discovers it on the go.

Pick wrong and you either pay for non-determinism you didn't need, or run a stale plan.

Voting vs Reflection

Multiple calls, opposite reasons

Voting keeps reviewers apart: disagreement is a measurement.

Reflection shows the output to the critic on purpose: the goal is improvement, not confidence.

Collaboration vs Supervisor

The difference is context

Collaboration shares the thread and allows backward handoffs.

Supervisor isolates each worker, so one guess can't contaminate another.

[34:30 – 36:00] The fastest way to remember the patterns is in pairs. Planning vs ReAct: same job shape, opposite control flow. Planning fixes the order, ReAct discovers it. Voting vs Reflection: both make multiple calls, for opposite reasons. Voting isolates reviewers because disagreement is data. Reflection deliberately shows the critic the output because the goal is improvement. Collaboration vs Supervisor: the difference is context. Shared thread and backward handoffs, versus strict isolation.

Before you reach for any pattern

Four checks — one "no" means change the design

01

Is the task genuinely multi-step and hard to fully specify?

02

Does the outcome justify the cost and latency?

03

Do you actually need the model to do it?

04

Can you catch errors, and can the app recover from them?

Source: Anthropic, Building effective agents

[37:00 – 38:00] Four checks from Anthropic's own guidance on when to build an agent and when not to. Is the task genuinely multi-step and hard to specify? Does the outcome justify cost and latency? Is the model actually needed? Can errors be caught and recovered from? A single "no" means change your design. This one paragraph alone explains where most teams go wrong.
